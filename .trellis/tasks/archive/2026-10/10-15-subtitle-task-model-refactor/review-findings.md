这条线程只做了一件事：**把"哪些写必须一起对"从一句口号，落到 9 行可核对的写集表上。**

所有分歧 —— 双尺子、V3 归属、丙/乙、C16、三条无写入时机的列、(a)/(b) —— 最后都收敛成那张表的一行、或一句话前提。

**而它真正改掉的不是 C40 一行，是判据的用法**：第 2 轮把 D-2 从"唯一尺子"降成"其中一把"，后面的分歧才收敛得下来。下一个读 handoff 的人一定会先撞上 §3.7.1 那份台账，而那份台账的问题正是**用一把尺子给出了两个相反的答案** —— 这句提示建议放在 handoff 的结论节开头。

### 0.1 术语（讨论里临时起的标签，handoff 里没有）

**甲 / 乙 / 丙** —— 三个候选答案，问的是同一个问题：**「当前上游是哪一版」由谁回答？**

| 标签 | 主张 | 白话 |
|---|---|---|
| 甲 | 由 `status` 回答 | 过时译文会被级联标成 `SUPERSEDED`，所以"是不是当前版"就等于"是不是 `READY`" |
| 乙 | 由 `lineage` 回答 | 读的时候比一下 `译文的 source_artifact_id == 当前 READY 的 CLEANED.id`，不等就重翻 |
| **丙** | 甲 + 级联标记**进事务** | 把"下游全标 `SUPERSEDED`"折进 CLEANED 换版的那个事务里 —— **owner 拍的就是这条** |

**上游 / `source_artifact_id`（lineage）** —— 产物链是 `ORIGINAL → CLEANED → TRANSLATED(lang)`，每一代基于上一代。"上游"指前一级；`source_artifact_id` 记的就是"这一版是从上游哪一版做出来的"。它有两个用途，**要分开看**：写入侧给级联用（`WHERE source_artifact_id = 旧 CLEANED.id`，没有它级联找不到要作废的行）；读取侧给 §7.5 的复用判据用（**这一侧随 丙 变成死条件，要删**）。

**(a) / (b)** —— C40 的两种替代记法：(a) 不要类级聚合标签、只用写集表；(b) 一个聚合根 `Workspace`。**已合拢在 (a)**，见 §4.2。

## 1. 起点：C35 / C40 到底错在哪

### 1.1 双尺子（§3.7.1 的核心问题）

§3.7.1 的台账在**同一个论证里用了两把尺子**：

- 拿「状态机该由自己的方法守着」（**封装判据**）把 `TaskRun` / `SubtitleArtifact` 提成聚合根；
- 又拿「约束在 DB」（**边界判据**）把 `Task` 降级为身份实体。

于是 §9.1 那条"`Workspace` 是弱聚合根、自相矛盾"不是孤立笔误，是**这把双尺子的必然产物** —— `Task` 用边界尺子量、`Workspace` 用封装尺子量，所以一个不够格、一个"弱"。

### 1.2 D-2 对单行状态机是**沉默**，不是排除

D-2 原文：*"聚合的判据不是'归类'，而是'哪些东西必须在一个事务里一起对'"*。

拿它量 `TaskRun`（V1 = 状态迁移合法）：答案只是"就一行"。那是一个**退化的作用域** —— D-2 既不能要求它有个边界，也不能宣布它不是边界。**宣布它不够格需要另写一条公理**（"边界必须是非平凡的"），这条公理本线程没有主张，也一并记在待裁里。

### 1.3 "机制一旦进判据，正反两个方向都推得动"

本线程双方各用过一次"机制反推资格"（一方用它把 `TaskRun` 说成不够格，一方用它把 `Workspace` 说成真聚合根）。这条对称性本身就是结论：**"聚合根"这个类级标签在本案里不承载信息** —— 见 §4。

## 2. 判据

### 2.1 D-2 的用法修正（本线程最重要的产出）

D-2 **不是唯一尺子**。判断写集要不要原子单位，至少还要看：

- 违规之后**能不能恢复**（新判据 R）；
- 机制够不够便宜（唯一索引能把"查 + 写"压成一条语句）。

### 2.2 新立判据 R —— 违规可恢复性

> **写集的原子性是否必需，取决于违规状态有没有恢复机制。**

本案的恢复机制**只有四个**：C15 启动收口、C25 读路径自愈、C17 人工重新触发、C26 手工对账（可选、未定）。

它是本案的真分水岭：W1 不可恢复 → 必需原子；W4 可恢复（重跑一次 RECLEAN）→ 非必需；W5 在 丙 之下不可恢复 → 必需。

## 3. 已定

### 3.1 owner 已拍定（唯一一条）

**「当前上游是哪一版」由 `status` 回答（术语表里的"丙"）：过时译文会被级联标成 `SUPERSEDED`，所以"是不是当前版"就等于"是不是 `READY`"；而级联标记与 CLEANED 换版在同一个事务里。** 2026-10-15 拍定，原话：*"每次 regenerate 的时候，之前的清洗和翻译都是被标记为废弃，等新的清洗洗出来后，他就是新的上游啊"*。

设计用**标记**表达"新清洗即新上游"，不做读取时比对。

**代价（必须写进文档）**：丙 之下，级联标记晚一步 → "新 CLEANED 已 READY、下游译文仍 READY 却指旧版"，而此时读路径已无 lineage 可比 → **静默交付错译文，且没有任何东西会来修它**（CLEANED 已 READY，级联不会重跑）。这是丙必须把标记折进事务的理由，也是它唯一的代价。

**连带**：

- **W5 无条件承重**；
- **§7.5 的 `source_artifact_id = 当前 CLEANED.id` 半句删掉**（丙 之后它永远不成为决定性判据，留一个永不生效的条件正是 D-6 要杀的死值）；判据收敛为 `TRANSLATED(lang, status=READY)`，与 §7.8 一致；

### 4.1 W1 是台账从未记过的一条真边界

`INSERT workspace` 与 `INSERT subtitle_task` 必须同生。只落前者 → **空壳 workspace** → `uk_source` 让下一次提交必定命中它，而 §7.1 步骤 3 的命中分支原文就是"**拿它的 `subtitle_task`**"（假定它存在）→ **永久卡死、无自愈路径**。

核过四个恢复机制一个都够不着：C25 只管文件缺失；§7.6 只写 `task_run` / `subtitle_artifact`；C26 按原文只"报孤儿与悬空"；C17 是人工重触发（但重触发会命中空壳，同样拿不到 task）。

### 4.2 为什么"两个聚合根"和"一个聚合根"都不成立

- **两个聚合根**不成立：`Task` 就是 `subtitle_task`，而**一个实体不能既是 A 聚合的内部实体、又是 B 聚合的根**（经典 DDD 明令禁止实体跨聚合）。
- **一个聚合根 `Workspace`（含全部）**不成立：那是 **god aggregate**，形状与被作废的 C35 一模一样（只是换个根）；而且**根上没有乐观锁版本列**，本设计的并发控制实际由 `uk_active_run`（**子行**唯一键）承担 —— **标签与实际机制不配对**；再加上 §8.1 已写定"每表一个 port"、§7 全篇查询都是 `WHERE task_id=?`（按身份引用），那正是"它们不在同一个聚合里"的写法。
- **"切两个小聚合"这个出口是空的**：artifact 集需要一个根，而唯一自然的根 `subtitle_task` 已按"根也是成员"归属第一个聚合，所以它的根只能是一个本设计没有的新东西（如 `ArtifactSet`）。该出口要么等于 (a)、要么等于新造概念 —— **它反过来加强 (a)**。

### 5.2 机械订正（建议批量点头）

**③ C16 撤销 + run 级无条件 `finally`** —— ✅ **已定（handoff C43 / C44 / C45 / C46）**

- C16 为什么净零：`owner_instance` 是**进程级** UUID，所以"本进程里线程死了"那一行的 owner **就是本进程** → 落进 §7.7 的"是本进程 → 409"分支 → **它自称要堵的缝，正是它唯一堵不住的那格**；另一半（owner ≠ 自己）在 C39 之下**不可达**（上个进程的残留已被 C15 在"早于接受请求"时清掉）。带进来一列 + 一段分支 + 一个判断，换到 0。
- 为什么必须换 `finally`：`uk_active_run` 挂在 `status='RUNNING'` 上，**一条收不了口的 RUNNING 行会永久占住该 task 的互斥直到进程重启**（mutex 泄漏）。C16 就是为堵这个泄漏而生的，它堵不住，所以替换品不是保险、是唯一兜得住的东西。
- **落位（本线程一致）**：收口点在 **run 的异步执行体那一层，一个点，所有 `run_type` 共用**。包住异步执行体，除非已落终态一律置 `FAILED`；流程内的各 catch **只负责丰富 `error_message` / `current_stage`**，不决定终态。于是 §7.3/7.4/7.5 里那三句"失败 → FAILED"退成**描述**，不再是三处实现 —— 这样 D-6 在 `run.status` 上才是"确定的触发点"。
- 附带一句（否则读的人会以为有了 `finally` 就不用启动收口）：**`finally` 是收窄不是证明** —— 它自己那条 UPDATE 失败（DB 断了）或 JVM 被杀，行还是停在 RUNNING，**那仍归 C15**。

## 9. 讨论底稿：文件与 DB 的一致性

> 这一节是 D1 的分析材料，供开新会话时接着谈。**结论部分（C50/C51/C52）已定并写进 handoff**；**D1 的三类残留窗口仍是待讨论项**。

### 9.1 前提：文件系统**不提供**事务

不是"没做好"，是它不提供，而且不会有。所以问题不该问成"怎么让文件操作进事务"，而该问成：

> **这个操作的中间态长什么样？能不能接受？谁来收尾？**

### 9.2 主流五招

| # | 招 | 要点 |
|---|---|---|
| ① | **原子替换** | 写临时文件 → `rename()` 到正式路径。POSIX 保证**同一文件系统内**原子 —— 正式路径上要么完整旧文件、要么完整新文件，没有中间态。Java：`Files.move(tmp, target, ATOMIC_MOVE)`。坑：跨盘会退化成 copy+delete；掉电场景要 `fsync` 文件与目录 |
| ② | **顺序纪律** | 写：先文件、后提交 DB；删：先标 DB、后删文件。见 C51 / C22 |
| ③ | **孤儿回收** | 崩了总会留孤儿。数据湖做法（Iceberg / Delta 的 `VACUUM`）：先提交元数据、后删文件，删不完的下次再删。本项目 = C26 的手工对账 |
| ④ | **内容寻址 / 不可变命名** | 文件名带 hash 或 revision，**永不覆盖**。新版本 = 新文件；旧的靠"没人引用"回收。好处：**"同名被覆盖"这个动作根本不存在**。代价：要 GC，且"当前是哪一版"必须由 DB 指认。Git / 数据湖的做法 |
| ⑤ | **原子换目录 / 换指针** | 整批文件写新目录，一次 `rename` 或 symlink 换"当前指针"。好处：**一批文件同时生效**。代价：路径必须带版本，读路径都得走指针 |

### 9.3 本项目选了 ①②③，放弃 ④⑤

放弃 ④⑤ 的原因就是 **C24**：文件名不带 revision、物理上每 `(type, lang)` 只留一份 —— "已交付的那一份在用户自己机器上，本地回收无损"。

**代价 = D1 的三类残留窗口**（都不留半成品、都能靠重跑收敛）：

1. 文件已替换、DB 事务未提交 → 拿到**更新的**内容；
2. 同一代产物多个文件之间毫秒级不同步（① 是逐个文件原子的）；
3. 孤儿文件（崩在删文件之前）。

### 9.4 崩了怎么"回滚"：没有 rollback，只有 roll-forward

数据库能回滚是有 undo 日志；文件系统没有，**改了就是改了**。所以设计的原则是**不让"需要回滚文件"这件事发生**，崩了直接**向前重做**。两个前提：

- **产物是可重新生成的缓存**（D-4）；
- **文件操作幂等** → 由此推出硬规矩：**凡是不幂等的文件操作不能进管线**（典型反例：往文件里追加；产物必须**整体重写**）。

逐崩溃点（以 RECLEAN 为例，顺序：算 → 写临时 → 原子替换 → 提交事务 → 删下游）：

| 崩在哪 | DB 说 | 盘上 | 后果 | 收敛 |
|---|---|---|---|---|
| 算的当中 | 旧版 READY | 旧内容（没被动过） | 无 | 重跑 |
| 临时文件写完、还没替换 | 旧版 READY | 旧内容 + 孤儿临时文件 | 垃圾 | 重跑 |
| 替换了 1/3 | 旧版 READY | 新 mixed 旧 | 这一代内部不一致 | 重跑 |
| 替换完、事务未提交 | 旧版 READY | 全新内容 | 内容与 DB 记录不一致（但内容完整可用） | 重跑 |
| 事务提交后、还没删下游 | 新版 READY | 新版内容 + 下游孤儿 | 垃圾 | 不用管 |
| 删下游删一半 | 新版 READY | 部分孤儿 | 垃圾 | 不用管 |

**副产品：查出"C50"那条缺口** —— 既然"文件存在"被当作断点复用的判据，那**中间产物也必须由原子替换产出**，否则崩了会留下半成品被当成成品复用，**而这是唯一一类不能靠重跑收敛的错误**（重跑会跳过它）。已定为 C50。

### 9.5 版本回退（已定：本次不做，见 C52）

将来要支持"回到上一版"，**改动是局部的**，因为位置已经留好：

| | 现在 | 将来 |
|---|---|---|
| 表结构 | `revision` 列 / `status` / 路径列都在 | **不用改** |
| 读路径（列产物、下载、复用判据） | 读 DB 里的路径列 | **不用改** |
| 产出时的文件命名 | 扁平（`clean-segments.json`） | 加版号（`r2/clean-segments.json` 或 `clean-segments-r2.json`） |
| 换版时 | 清空旧行文件列 + 删下游文件 | **删掉这两步** |
| 回退动作 | —— | 一次双行 status 交换（形状同换版） |
| GC | —— | 新增，手工触发即可 |

**唯一不免费的**：现在隐含"revision 越大越新"，回退会破掉它。两条解法：(a) 交换 status（简单，接受语义松动）；(b) 回退也插一条新行（保住单调性，但要按引用计数删文件）。(a) 够用。
