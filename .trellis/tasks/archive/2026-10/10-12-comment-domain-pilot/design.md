# domain 试点 · 技术设计

> **标准不在这里。** 本子任务的技术设计（十三条禁令、内容分流表、验证策略、风险处置）
> **全在 `.trellis/spec/guides/comment-guidelines.md`（正典）**，本文件不复制——复制必然漂移。

> 本文件只记录**本层独有的**设计判断。

## 本层独有的三点

### 1. 为什么 `package-info.java` 排在执行顺序最前

三个 `package-info`（subtitle / task / media）既是收口对象（都带变更史标记），
又是**上移的目的地**。先做它们，后续 A 组各文件才有地方搬——否则会退化成「先删、回头再想搬哪」，
而「删了没搬」正是父 `design.md` §6 列为第一位风险的情形。

### 2. 为什么 C 组是「对照面」而不是「待办」

`TranscriptionCommand` / `AudioSource` / `ASRProvider` 是既有 spec 亲手点名的**注释正面例子**。
把它们纳入工作集，期望结论是「基本不动」。若收口时发现它们也得大改，说明新标准与既有正面例子
冲突——那是**标准写歪了的信号**，要回改标准，而不是把这三个文件改掉。

### 3. 「标准补充」机制

收口时凡遇到正典没覆盖的情形，就地记进本子任务 `implement.md` §2，**不默默自行裁量**。
这一节是校准轮的主要产出：规则的**边界情形**只有在真实文件上跑过才暴露得出来。
门 G1 上交给用户时，这一节比 diff 更值得看。

## 不做的设计

- **不抽工具脚本**去批量处理注释。规则的判据是语义（「删了会不会有人踩坑」），
  正则只能识别机械特征（日期、`design 决策`），后者已由钩子承担；
  批量正则改写注释会误伤，收益不抵风险。
- **不引入 checkstyle / javadoc 插件**。pom 里现有零注释类校验，本任务不新增构建期依赖
  （quality-guidelines 明文反对无谓依赖）。
