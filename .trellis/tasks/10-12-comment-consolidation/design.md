## 2. 移动的目的地与代价

四处目的地都不新造：`package-info.java` 已有 20 个（8–22 行，承接能力已验证）；
`.trellis/spec/` 已有同类文档（`logging-guidelines.md`、`error-handling.md`）；
任务卡 `design.md` 20+ 份（140–453 行，[实测](./implement.md)含被删注释的原话）；
`git log` 天然是变更史的家。

**必须承认的代价**：任务卡归档在 `.trellis/tasks/archive/` 下，从代码里删掉后
**可发现性下降**——以后维护者不会主动去翻归档。缓解两条：

1. 正典里写明「改某段代码前想找『为什么』，先翻 `.trellis/tasks/archive/` 下的 `design.md`」；
2. 对**真正反直觉、删了会被误改**的那类，代码里保留**一句** why——但不保留出处引用。

## 3. 正典落位

新建 `.trellis/spec/guides/comment-guidelines.md`。

**为什么放 `guides/` 而不是拆进两份 `quality-guidelines`**：注释规则同时管前后端，

**形态**：裸装 `.git/hooks/pre-commit`（用户 2026-10-12 选定）。命中即非零退出、打印违规行。
**由收尾子任务（frontend）安装，AC7 验证。**

**脚本全文 · 模式清单 · 已知缺口（不入库 / `--no-verify` 可绕 / 模式非穷举 / 已知误报 /
Git for Windows 的 sh 与 CRLF / 扫描面）——全在正典 §六**，此处不复制（复制必然漂移）。

**模式清单只住正典 §六**（脚本全文 + 模式表都在那一段）。其他文件一律**引用不复制**——

## 5. 验证策略

| 验收 | 手段 | 判定 |
|---|---|---|
| AC1 变更史归零 | 上表模式 `grep -rn` 三个扫描面 | 命中 = 0 |
| AC2 长尾收敛 | 块行数统计**只作粗筛**；>15 行的逐个复核「是否只回答那四件事」 | 复核通过的进例外登记，登记须写明内容为什么砍不动 |
| AC3 上移落地 | 每层抽 3 类，回查 `package-info` / spec / `design.md` | 有对应表述 |
| AC4 腐坏订正 | 子任务 `implement.md` 里的清单 | 逐条已订正 |
| AC5 行为不变 | `cd backend && rm -rf target/surefire-reports && JAVA_HOME=/f/java_soft/java21 mvn -q test` | 全绿，基线实测 |
| AC6 正典与指针 | 文件存在 + 两份 quality-guidelines 已改指针 | 人工 |
| AC7 钩子生效 | 故意写一个日期，`git commit` | 被拦 |

**「只改注释」的复核**：`git diff -w --stat` 通读，确认没有非注释行进入。注释改动不参与编译，
所以 AC5 大概率恒绿——它的价值在于排除「手滑改了代码」这一种失误，而不是证明注释改对了。

## 6. 风险与处置

| 风险 | 处置 |
|---|---|
| 误删承载知识的 why | 先判断能否上移到四处目的地；能则移、不能则就地压缩成一句，**不直接丢** |
| 找不到原决策，只能猜 | 回查 `.trellis/tasks/archive/**/design.md`；查不到就在 `implement.md` 登记「无出处，保守保留」 |
| 把腐坏的注释当成正确依据 | 与代码对读后再动；矛盾时改注释不改代码，并登记 |
| 标准跑偏波及 144 文件 | domain 试点先钉死；试点审查通过前，其余五个子任务不开工 |
| 长尾界定主观 | AC2 的 `>15 行` **只作粗筛**，真判据是「这块是否只回答那四件事」；复核过的进例外登记——把主观判断逼成**显式清单** |
