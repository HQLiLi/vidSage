# 注释收口：删变更史与决策记录、修正粒度错位

> **状态：planning**（父任务卡只定义需求、边界与跨子任务的验收标准，自己不写代码）。
> 子任务 1–4 已收口归档，进度与门见 `implement.md` §0。
> 粒度标准（正典的正文）在 `.trellis/spec/guides/comment-guidelines.md`。六条子任务各自收口一层，
> 父任务本身不改代码。
> 来源：2026-10-12 会话取证 + 四轮 grill 共识。

## Goal

把注释从「design.md、方法注释、API 文档、实现备注揉在一起」的状态，收敛成**按抽象层级分容器**的写法：
设计理由回任务卡 `design.md`、包级架构回 `package-info.java`、流程与事件口径回 `.trellis/spec/`、
变更史回 `git log`——代码里只留**对外契约**与**删了会踩坑的那个为什么**。

并落地两件配套：一份**跨端注释写法正典**（`guides/`），一个**防复发的 git 钩子**。

## 问题定义（2026-10-12 取证结论）

三层病灶，分开治：

**A · 粒度错位（结构问题，本任务的主因）**
同类内容按抽象层级本应有不同容器，现在全挤在 Javadoc 里、按同一视觉权重排：

| 现在写在注释里的内容 | 它真正的家 | 实例 |
|---|---|---|
| 为什么这样设计、否决了什么、代价 | 任务卡 `design.md` | `TaskConflictException`「为什么此刻引入第一个自定义异常」 |
| 包/层怎么分、谁调谁 | `package-info.java` | `SubtitleCleanupCoordinator` 类注释里的「管线形状」 |
| 流程步骤、进度事件序列 | `.trellis/spec/` | 同文件方法注释里的进度事件 `<ul>` |
| 什么时候改的 | `git log` | 「2026-10-12 起」「（design.md 权衡记录）」 |

> ⚠️ **上表是诊断期的取证结论，不是规则。** 正式的分流规则见正典 §二（比它多两行、且是唯一的规则正文）。
> 两处不一致时**以正典为准**——本表保留在此只为说明「当初为什么判定这是结构问题」。

**B · 密度过高（体量问题）**
main 源码 669 个 Javadoc 块，中位 4 行、均值 5.5 行——所以「偏多」是**长尾**，不是普遍超标：
`100 块 >10 行`、`42 块 >15 行`、`10 块 >20 行`。另有 **44 个文件**带变更史/决策标记
（`20xx-xx-xx` 53 处、`design 决策` 15 处、`design.md` 9 处、「迁移前/字节一致/旧守卫」5 处）。

**C · 注释已在腐坏（正确性问题）**
`TaskResponse.from` 的 Javadoc 是断句残句（「产物清单逐元素映射为」就没了）；DTO 层 13 个文件、
50 个字段把同一段文字既写 `@param` 又写 `@Schema(description=…)`。密度高的注释更容易腐坏——
这是「多」的真实代价，也是本任务不能只做「删」、必须顺带订正的理由。

## 范围

**做**：后端 main 全部（144 文件）、后端测试（56 文件）、前端 `src`（25 文件）；
两份 `quality-guidelines.md` 的注释章节改写；新建 `guides/` 注释写法正典；装 git 钩子。

**不做**（明确排除，避免范围膨胀）：

- **不动代码行为**。本任务只改注释与文档，不改一个表达式、不动一个签名。若发现注释与代码矛盾，
  **订正注释**、不改代码；真觉得代码错，另开任务。
- **不改 `@Schema` 落位**。DTO 层 `@param` 与 `@Schema` 文案重复已知（13 文件 / 50 字段），
  本任务**绕开**：只在两份文案**已经不一致或腐坏**时订正其中一份，不主动删任一侧。
  理由：用户另有未决口径在自行推进，本任务不预判它的结论。
- **不做无差别重写**。只动「长尾块」与「带变更史标记的文件」；中位数那批本来就不长的注释，
  没有具体毛病就不碰。
- **不动 `prototype/`、`asr-service/`、`tools/`、`backend/data/`**。

## 验收标准（跨子任务）

- [ ] **AC1 变更史归零（机器可判）**：按 **`.trellis/spec/guides/comment-guidelines.md` §六 的模式清单**，
      在 `backend/src/main/java`、`backend/src/test/java`、`frontend/src` 三个扫描面 `grep`，命中数均为 0。
      **模式清单只住正典 §六**（脚本全文与模式表都在那），本文件不复制——复制必然漂移。
      **注意模式天生追不上自然语言**：`与原 X 一致`、`原为…`、短任务号 `09-28` 这类拦不住，靠人眼通读。
- [ ] **AC2 长尾收敛（人工判）**：**任一 Javadoc 块只回答四件事**——它是什么 / 不变量是什么 /
      和其他类型什么关系 / 边界在哪。公式、参数语义、流程细节出现在**成员注释**里不算违例（那是它们的家），
      出现在**类注释**里才算。
      **判读统一走正典 §一 那把尺子**（2026-10-13 入正典，web 层实测有效，**不止适用于长尾块**）：
      读者读完**会不会改变接下来要做的事**——会 → 留；不会 → 删（「解释既成安排」那一族，五种形态见正典 §一）。
      **删完回查两件事**：悬空引用与注释块内的裸空行。
      **`>15 行` 降级为「触发人工复核」的信号**（2026-10-12 domain 试点改判）。三条校准点：

      15 行块是 80% 噪音——**数行数既能放过噪音，也能误伤好块**。

- [ ] **AC4 腐坏订正**：发现的断句残句与失实表述逐处订正，并在子任务 `implement.md` 留清单。
- [ ] **AC5 行为不变**：`mvn clean test` 全绿；基线以实测为准（不引用历史数字，历史值 570 已被刷新）。

## 约束

- **只改注释**：diff 里不应出现任何 `.java` 的非注释行变更（`git diff -w` 复核）。
- 语言中文；首行用大白话，避免正式抽象腔（既有约定）。
- 每个子任务改完**停下等审查**，不自行提交（分支工作流硬规则）。
