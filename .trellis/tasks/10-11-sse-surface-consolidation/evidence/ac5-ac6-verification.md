## AC5 瞬时断连可见

用 AC5 允许的两种复现方式之一——**Playwright 拦截 `/api/tasks/*/events` 先 abort 再放行**
（另一种「代码外停/启后端」未采用：后端进程内跑管线，杀掉会连带终止任务本身）。

步骤：提交一条真实任务（taskNo `c9b63446b4524d55a8bfd77788343c88`）→ 装上 `route.abort()`
→ 打开工作区页 → 观测 → `unroute()` → 再观测。

| 观测点 | 结果 |
|---|---|
| 提示条文案 | `连接中断，正在重连…` |
| 出现耗时 | **3.4 s**（≈ 两次连续失败 × EventSource ~3s 重试间隔；`RECONNECT_HINT_AFTER = 2`） |
| 是否遮挡 | 否——同屏进度卡仍在（页面文本 `任务排队中，等待开始处理… 0% …`），提示条是根级 `shrink-0` 横条，推开而非覆盖 |
| 放行后 | 提示条消失（`waitFor({state:'hidden'})` 通过，元素计数归 0） |
| 事件流是否续上 | **是**——后端日志出现该 taskNo 的 `订阅任务进度`（17:20:04.523，即放行后的第 2 次连接；被 abort 的那些请求在浏览器侧就断了，从未到达后端），随后 `查询任务` + `下载任务产物` ×2（终态静默刷新 → 建 cues），页面切到就绪双栏 |

截图：`ac5-reconnecting-ready-state.png`（就绪态下的提示条；可见它落在 `WorkspaceHeader` **之上**）。

> 说明：AC5 要求「进度无感恢复」。本轮的证据链是「放行 → 重连 → 后端推当前 DB 快照 →
> 页面直接进入就绪态」；任务在观测窗口内跑完，故没抓到「进度条从 X% 继续涨」的中间帧。

### ⚠️ 未达成的部分：`/events` 单独失败的那条路无渲染出口

AC6 的正文还要求「重拉一次快照确诊，…其余情况显示现有**通用错误卡**」。这条路由
`diagnoseFatal()` 写入 `loadError`，但视图的渲染优先级是：

```
就绪态分支  isSucceeded && taskView      ← 最外层，优先于一切
非就绪态：  进度卡 isRunning → 失败卡 isFailed → 错误卡 loadError → loading
```

逐一对照，`loadError` 由 `diagnoseFatal` 写入时**没有任何状态能渲染出这张卡**：

| 致命断连时任务状态 | 实际渲染 |
|---|---|
| RUNNING / PENDING | 进度卡（`isRunning` 先判） |
| FAILED | 失败卡（`isFailed` 先判） |
| SUCCEEDED（如翻译中） | 就绪双栏（最外层分支） |
| taskView 为空 | loading（且 `diagnoseFatal` 提前 return，压根不写） |

即 R4 的「致命类不再静默」**实际未达成**。**处置：2026-10-11 项目所有者拍板「先登记，不改」**——
本任务 AC7 的「唯一差异是新增 `terminal` 字段」对照需要一个干净的基线，塞进视图改动会让它失真。
缺口已登记进 `prd.md` 的 Out of scope（见该文件同日条目）。
