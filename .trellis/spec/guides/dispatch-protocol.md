## 1. 批次并行默认规则

**规则**：规划期按依赖图给批次分层；**同层无关联批次并行派发，跨层串行**。串行是例外，不是默认——串行默认让多数任务白丢 30–40% 墙钟。

**并行准入条件**（两条同时满足才允许并行派发）：

1. **依赖分层清晰**：批次间依赖可画成有向无环图并分层；同层任意两批之间不存在「一批的输出是另一批的输入」或「两批写同一文件」的关系。
2. **文件所有权清单必填**：每批派发词必须带「允许创建/修改清单」（逐文件列出，不得写「及相关文件」）；写入清单之外的文件视为越权。

**批次规模上限**：单个实现派发覆盖 implement.md 步骤 **≤3–4 步，超过必须拆批**。

- 理由（数字）：每批固定上下文（规范 + 任务工件）≈ **15–20k token**，批越大这笔开销摊薄得越少、单批轮数越失控。对照基线：实现批次 A 一次覆盖 implement.md 第 1–4 步，**81 次工具调用**（execution-log #1）；全量检查 **97 次调用**（execution-log #4）。
- 反向同样禁止：一步一派的极端拆分不做——固定上下文 × 派发数反噬总 token。

## 2. 检查拆面

全量检查默认拆为三个**并行读面**：

| 读面 | 检查内容 |
|---|---|
| 规范关 | 是否符合 `.trellis/spec/` 相关层规范 |
| 契约关 | 接口签名 / 数据结构 / import 路径的跨批一致性 |
| 逻辑关 | 变更逻辑正确性、边界条件 |

**读面纪律**（每面都是硬规则）：

- 纯读：不跑任何命令、不写任何文件 → 无需隔离，同目录并行安全。
- 读取面 = `git diff` 变更清单 + 派发词指明的引用锚点（涉及的规范文件 / 接口文件 / 模块路径）；**禁止全量读仓库**。
- 三个读面并行派发，互不等待。

**命令关单独走**：type-check / lint / build 由**单独一个代理或主线**执行，不与读面混编；**禁止并发跑 npm 命令**（node_modules / .tmp 竞态）。

收益锚点（估算，台账复核）：检查读面 token −30~40%（基线全量检查 97 次调用 / 25 min，execution-log #4）。

## 3. 减轮数与省前缀三条款

以下三条作为**硬规则写进每个派发词**（镜像落点：workflow.md 注入块）：

1. **读齐再动手**：动手前一轮并行读取所需文件；禁止一回合单动作串行磨。
2. **验证链每批一轮**：批次收尾一轮并行跑 type-check + lint；build 留任务收尾只跑一次。
3. **定位式读取优先**：先 grep 定位，再按 offset/limit 读片段；同一文件不整读两遍；禁止为确认而重读大文件。

**成本模型**：累计 token ≈ 轮数 × 前缀。条款 1、2 砍轮数，条款 3 砍单轮前缀体积。预期 input −20~30%（估算，台账复核）。

## 4. 档位判据（协议层）

对每个批次做**三问二值**测试（每问只有「是 / 否」两个答案）：

| # | 问题 | 「是」的含义 | 指向 |
|---|---|---|---|
| ① | 有设计成分吗？ | 引入新抽象 / 新契约 / 需要做取舍 | 「是」→ 高档 |
| ② | 错了有兜底吗？ | 后续检查与合并裁决兜得住该批的错误（注意：**检查面与合并裁决自身无兜底**——它们是最后一道网） | 「否」→ 高档 |
| ③ | 能写成无歧义清单吗？ | 清单已存在且由高档产出（规划期没产出清单 = 「否」） | 「否」→ 高档 |

**判定规则**（可执行，无中间档）：

- 任一问指向高档（①「是」∨ ②「否」∨ ③「否」）→ **高档执行者**；
- 三问全部指向低档（①「否」∧ ②「是」∧ ③「是」）→ **低档执行者**（协议层角色名，不绑定任何工具机制，工具映射见 §7 适配层）；
- 拿不准 → **高档**（宁可多花 token，不可错批降档）。

**低档批次纪律**（两条硬规则）：

1. 只执行派发词清单内动作；
2. 遇清单外情况（缺前提、需求冲突、歧义、清单覆盖不了的任何情况）**必须停下上报主线**，禁止就地降质决策。

预期收益（估算，台账复核）：机械批次生成 token −30~50%。

## 5. worktree 仪式与合并规程

### 5.1 隔离默认与例外

- **默认**：并行实现批次**每批一棵 git worktree**。动机 = 验证隔离 + 杜绝同名文件静默覆盖：全项目 type-check 会撞见兄弟批次半成品；同目录并行写同名文件 = 后写者静默覆盖先写者，且无任何报警。仪式成本 ~4–6 min，远小于并行墙钟收益。
- **例外**（同目录即可，仅两条）：① 纯读的并行检查面（§2，不写文件）；② 不跑验证的纯写入小批（无验证可隔离；其所有权清单不得与兄弟批次相交）。

### 5.2 仪式（有序 8 步）

1. 上游批次先 commit——**批次完成即 commit**（新增约定；worktree 需要已提交基座）；
2. `git worktree add` 每批一棵（用 §5.3 脚本：`tools/trellis-worktree.sh <batch-name>`）；
3. 树内各自 `npm ci`（缓存热 ~1–2 min；**禁止 node_modules 软链共享**——tsBuildInfoFile 竞态）；
4. 派发词指明 worktree 路径；
5. 派发词必含：**允许创建/修改清单 + 禁建清单（上游已有符号及其 import 路径）**；
6. 各批独立写码 + 独立全量验证（type-check + lint + build 在自己树内完成）；
7. 主线 `git merge --no-ff` 逐批合入（机械冲突按 §5.4 SOP；语义冲突按 §5.5 升级）；
8. 删树（`tools/trellis-worktree.sh --clean <batch-name>`）→ 主线收尾验证。

### 5.3 worktree 仪式脚本接口规格（`tools/trellis-worktree.sh`）

脚本由本任务 tools 批次按下述规格实现；协议只锁接口，实现照单执行：

| 调用 | 行为 | 硬约束 |
|---|---|---|
| `tools/trellis-worktree.sh <batch-name>` | 对该批次执行 `git worktree add` + 在树内 `npm ci` | **幂等**：重复执行安全（树已存在则跳过 add；依赖已就绪不重复全量安装） |
| `tools/trellis-worktree.sh --clean <batch-name>` | 删除该批次 worktree | 同上幂等 |

- **非交互**：任何执行路径不得依赖交互输入；
- **Git Bash 兼容**：本项目运行环境为 Windows / Git Bash。

### 5.4 合并 SOP（机械冲突，主线自主执行）

四步，按序执行：

1. **定权威取并集**：同名文件 / 重复定义逐项判定，取并集，不丢任何一方有效改动；
2. **归一 import**：路径 / 顺序 / 别名统一到一侧；
3. **type-check 找断点**：以编译错误定位漏改点；
4. **删重复 + 一轮验证**：删掉重复实现，合并收尾 type-check + lint 一轮通过。

规模上限：冲突涉及 **>3 文件**时，可转派低档修复代理执行本 SOP；裁决权仍在主线，不上移也不下放。

### 5.5 升级规则（两条，任一触发立即上报用户）

1. **语义级冲突**：两批对同一职责给出不同字段设计 / 不同行为——机械规则定不了对错 → 升级用户裁决，呈**两版本对照 + 主线推荐**；
2. **合并后验证不过且修不动** → 上报，不得自行放低验证标准。

### 5.6 共享物上提（规划期义务）

规划期发现两个并行批次都需要同一共享物（类型定义 / 工具函数 / 常量）→ **上提到共同上游批次**，禁止两批各自重复定义（重复定义是 §5.4 机械冲突的主要来源）。

## 6. 执行台账

- **落点**：任务目录 `research/execution-log.md`（先例：`.trellis/tasks/archive/2026-10/10-03-vidsage-fe-v0/research/execution-log.md`）。
- **记录时机**：**每个派发结束即记**，不攒批。
- **必填列**（8 列，缺一不可）：

| 列 | 内容 |
|---|---|
| # | 序号 |
| 派发 | 批次名 |
| 子代理 | 类型（如 trellis-implement / trellis-check / 主线） |
| 覆盖步骤 | implement.md 步骤号或范围 |
| 开始 epoch | 派发开始时刻 |
| 结束 epoch | 派发结束时刻 |
| 耗时 | 结束 − 开始 |
| usage 三件套 | `subagent_tokens` / `tool_uses` / `duration_ms` |

- **字段边界**：台账只固化宿主已报告的 usage 三件套；宿主未报告的字段（如峰值上下文、压缩次数）**不得编造入表**。
- **用途**：后续调优的数据基线。下一个按本协议派发的任务，用台账对照基线（105 min / 184k 输出 token；六派发表观速率 10–40 tok/s）复核各项估算收益。
