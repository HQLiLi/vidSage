# 注释写法（项目级正典）

> **地位**：项目里**唯一**一份注释规则。前后端共用——规则正文只此一份，
> `backend/quality-guidelines.md` 与 `frontend/quality-guidelines.md` 的注释章节只留一行指针
> 加本语言的例子。
>
> **为什么单独成篇**：注释规则同时管 Java 与 TS，散在两份 quality-guidelines 里必然漂移。
>
> **这套规则治的是什么**：历史注释把四种内容揉在了同一个粒度上——任务卡的**设计理由**、
> 公开 API 的**契约**、包级的**构件地图**、实现层的**坑**。看着都像「好注释」，合起来就是
> 每段都得读完才知道要不要读。解法不是删，是**分流**。
>
> **七章地图**：§一 第一原理 · §二 内容分流表 · §三 按层级的写法（**十三条禁令**）·
> §四 正例反例 · §五 去哪找「为什么」+ 规则边界 · §六 防复发钩子 · §七 元规则（标准只住一处）。
>
> **子任务怎么用**：先读 §三 的十三条禁令，收口时按 §二 分流；**本文件是唯一正文**，
> 任何任务卡、子任务 prd 里的说法与它不一致时，**以本文件为准**。

---

## 一、第一原理

**删了会不会有人踩坑。** 会 → 留；不会 → 不留。

这条不新增、不替换任何既有约定，下面只是把它落到具体位置。

配套的两条既有口径继续有效（原文见两份 `quality-guidelines.md`）：

1. **写与删是两件事**：写的人一律先写全，判断「有没有意义」是用户的活。
   **「这里没有注释」不等于违规**——很可能是用户有意删的，不要引硬线要求补写。
2. **新代码跟随本文件**，不跟随旧代码的密度。

## 二、内容分流表（治「粒度错位」的正解）

拿到一段注释，先问「它是什么」，再送它去该去的家：

| 这段在说什么 | 该在的家 | 代码里最终留什么 |
|---|---|---|
| 为什么这样设计、否决了哪些备选、代价是什么 | 任务卡 `design.md` | 只在**反直觉到会被误改**时留**一句** why |
| 什么时候改的（日期 / 任务号 / `design 决策 N` / 「迁移前…」「旧守卫…」） | `git log` | **不留** |
| 包/层怎么分、谁调谁、本包有哪些构件 | `package-info.java` | 类注释**不复述** |
| 流程步骤、进度事件序列、阶段词表 | `.trellis/spec/` | 方法注释**不写流水账** |
| 对外契约：语义 / 单位 / `null` 与缺省含义 / **负面约束** / 异常 | Javadoc `@param` `@return` `@throws` | **留** |
| 实现层的坑：这行为什么不能删 | 行内注释 | **留** |

**上移优先于删除**：能搬去上面四个目的地（任务卡 / `git log` / `package-info` / spec）的先搬，
再从代码里删本地副本。查不到出处、又确实是 why 的，**就地压缩成一句**，不直接丢。

**订正惯例（沿用 `doc-revision-convention`）**：发现失实、残句、笔误 → **直接改写为现状**，
不留「原为…」「已废弃」的痕迹。注释不留变更史，**这条同样适用于「怎么改注释」本身**。

## 三、按层级的写法

### 先看十三条禁令（2026-10-12 定，`SubtitleRoute` / `SourceUri` / `VideoTask` 三轮校准）

**1. 契约注释必须自洽，不依赖别的类的知识。**
不写「与此处 `AudioContainer` 派生 `.m4a` 同构」「同 `SrtRenderer.toSrt` 的处理」
「与 `CheckpointPolicy` 的既有分工一致」——读者不一定知道那个类；而且那个类一改，这里就假了。

**2. 不写「当前实现的快照」，改写「职责边界」。**
「本枚举无字段无方法」今天真、明天加个 `isPlatform()` 就假——**但它假了不代表设计错了，
只代表注释写错了层次**。改成「本枚举仅定义取值域，不承载文件名、扩展名等派生逻辑」：
只要这个边界没变，加了方法注释仍然成立，而且信息量更大（它告诉后来者别往枚举里塞派生逻辑）。
同类待改：`不开放 setter`、`紧凑构造器只校验…`、`只声明上层真正调用的那一个重载`。

**3. 实现层的细节回到实现层。**
端口注释里不写「实现在 `infrastructure/…`（当前是 `Llm*`）」「由 Spring 注进来」
「带 listener 的便捷重载留给测试用」——这些会腐化（实现会换、测试会搬），归属实现层文档。
业务规则也一样：文件名怎么从 `name()` 派生、kebab token 长什么样，
**契约里只写「本枚举不负责文件名派生」这句边界**，规则写进真正负责它的地方。

**4. 事实必须与代码对得上，计数类陈述尤其。**
`SubtitleRoute` 原写「含**两个**目前产不出的值」——实际**三个**；
`TermVerification` 原写「**三条**同时成立才查」——实际四条。计数是最先腐化的东西，
腐化了读者会照着错的理解走。**能用「各 / 其中一个」就不写数字。**
**笔误、错字、断句残句同样算硬伤**（`它带**会**拒绝非法状态迁移` → `它带**有**`）——
这类肉眼可查，**定稿后通读一遍**。

**5. 同一文件内多处表述必须一致。**
同一份枚举里「含两个不产出的值」「目前不产出」「唯一产出」三处说法打架，
读者得回头对顶部说明。常量注释统一成同一句式。

**6. 不为「没发生的事」写辩护句。**
- 「**不另设**「字幕来源」枚举，避免两个真相源」——那个枚举不存在，读者也不会去找它；
  解释了不改变他接下来要做什么。
- 「翻译这一项**将来会去掉**」——预言会腐化：改动真发生时它变成陈迹，没发生时它是噪音。
  未来的改动归任务卡，不归代码。

**判据**：「你为什么不做另一件事」只有**读者本来就会去做那件事**时才值钱。
`WorkspaceKey` 的「刻意不做 12 位十六进制的正则强校验」值钱——那是防人来「修」的；
上面两句不值钱——没人会去建那个枚举，也没人会因为这句 prophecy 改变读法。

**负向边界句（「本 X 不承担 Y」）同样过这道判据。** 域内试点扫了全部 9 处，
**只有 2 处该删**（`SubtitleRoute` 的「不承载文件名派生」——没人会往枚举里塞；
两个字幕端口的「判据不进本接口」——原文自己就说那是实现细节）。其余 7 处全部留下，
因为各自防的是**读者真会去做**的事：

| 留下 | 防的是 |
|---|---|
| `CheckpointPolicy` / `SubtitleArtifactSpec`「SRT 不参与幂等」 | 拿 SRT 当检查点 → 空转写永远重跑 |
| `CleanseResult`「计数不参与任何判定」 | 拿计数做分支 |
| `SubtitleKeywordRepository` / `VideoTaskRepository`「本接口只说能做什么」 | 把 MySQL 漏进领域端口 |
| `SubtitleKeywordRepository`「分隔符不进本接口」 | 领域侧去碰 `U+0001`（而 `SubtitleKeywords` 里那个常量是 public，歧义真实存在） |
| `TermLookupProvider`「触发确定性不属于本接口」 | 把「哪些词要查」塞进 provider |
| `WorkspaceKey` / `TaskNo`「刻意不做 hex 正则校验」 | 有人来「修」它 |

**7. 不写「索引」——谁在用它、它有哪些方法、谁按变体分派到我。**
- 「这份清单由 HTTP 两个入口（提交任务 / 重新生成）与持久化层共用」——**grep 一下就有**，
  而且入口一增减就腐化（`SubtitleRoute` 原稿的「四个服务合流于此」是同一个毛病的重度版）。
- 「{@code MediaInput.getContentKey} 按变体分派到这里的静态工厂」——**调用方的行为**，写在类注释里
  会让读者以为本类和调用方有依赖。
- 「`resolveTargetLanguage` 归一化目标语种；`resolveSourceLanguage` 优先摘要推断…」——
  **把方法名复述成一段散文**，读者往下翻两行就看到签名了。
- 「触发经济学的判定见 `decide`，执行与记账见 `verify`」——同义反复。
- 「`VideoTaskServiceTest` 跨包复用公式断言」——**测试在哪里**，属禁令 3 的实现层细节。

四者都**删掉不损失任何信息**，留下来的代价是读者要读完这段才知道「这里没有新东西」。

**8. 契约必须可达——不承诺做不到的事。**
「同一输入必须规范化出同一串」是真不变量；「**不同**输入必须规范化出**不同**串」不是——
哈希碰撞无法排除，`绝对路径|大小|mtime` 也保证不了唯一。降级成「本类不承诺不同输入一定出不同串」。
**不降级的后果**：读者会写出依赖「无碰撞」的代码。
同类：`WorkspaceDir` / `MediaInput` 原写「唯一性**完全由哈希保证**」。
**自检**：类注释里每出现「必须 / 一定 / 保证 / 绝不 / 永远」，先问「这条我真能保证吗」。

**9. 用词必须准确——宁可不说，也不安一个不准的词。**
「大小 + mtime」不是「内容指纹」，是很弱的**身份指纹**（两个不同文件可以有相同大小与 mtime）。
叫它「内容指纹」会让读者以为它能在内容层面区分文件。

**10. 类注释稳定，成员注释精确——同一处细节只写一遍。**
- 类注释回答四件事：**是什么 / 不变量是什么 / 和其他类型什么关系 / 边界在哪**。
- 公式、参数语义、占位、`null` 处理一律下沉到成员注释：`SourceUri` 的类注释只写
  「有两条路线，各自以什么为身份」，公式见 `ofRemoteUrl` / `ofLocalFile`。
- **判据：改一处公式要改两遍 = 违例。** 类注释里出现方法名时，先自问「这个细节是不是该留在那个方法上」。
- 这条是禁令 5 在**类注释 ↔ 成员注释**这一维度上的推广。
- **验收口径**：块行数**只作粗筛**（`>15 行` 触发人工复核），真判据是「这块是否只回答那四件事」。
  数行数既放过噪音（`StageProgress` 15 行里只有一行带信息），也误伤好块（`SourceUri` 的四件事
  天然要 16 行）。复核后确认砍不动的，登记例外并写明理由——**不接受靠拆行凑数**。

**11. 措辞要经得起读。**
- **有第二读法就改写**：「本类**只在计算 key 时存在**」可读成「实例生命周期临时」，也可读成
  「只有一个用途」——后者才是本意 → 「本类**只用于计算 key**」。
- **不贬低别的写法**：「所以住在 domain 而不是**贫血的实体类**」读起来像在批评另一种做法 →
  「所以由 domain 承载，而不是只做数据容器的实体」。
- **不用内部讨论腔**：「四值**一次定死**」→「取值域**冻结**」——后者不会让人误解为「以后永远不能加值」。

**12. 横切策略写成显式约束，别混进字段语义。**
「来源：URL 原文或上传文件原始名（**日志不落原值**）」——「日志不落原值」是一条横切的日志 / 合规策略，
不是 `sourceUri` 的语义：读者会以为这个字段知道日志怎么打，而真正管日志的是别处；改日志配置的人
也不会回来改这里。写成**显式约束**：`<b>约束：本字段值不得直接写入日志</b>——含用户原始文件名，属敏感信息。`
**判据**：这条讲的是「谁在什么场合不能用它」，不是「它是什么」——后者留字段注释。
同类：跨层的鉴权 / 脱敏 / 并发约定，都别写成字段的定语。

**13. 名字对领域读者是费的，就用注释补一句用途。**
`isEventTerminal(TaskStatus, TranslationStatus)` 里没有任何 "Event"，读代码的人会问
「哪个 Event 的 terminal」。补一句「用于事件分发——返回 {@code true} 表示该任务不会再产生后续状态事件」，
这笔账就还上了。**这不是「复述方法名」——恰恰是名字没说清的那半。**

> 十三条合起来是一句话：**契约注释只回答「它是什么 / 不变量是什么 / 每个值什么意思 /
> 为什么这么留 / 和其他类型什么关系 / 边界在哪」，只写这个类真能保证的事，并且读一遍不打结。
> 它不回答「服务层怎么实现它」，不回答「我们当初忍住了没做什么」，不回答「现在有谁在调它」。**

### 类 / 接口

- 首行一句话说「是什么」，**大白话**（避免「契约 / 结构性 / 落点 / 载体」这类正式抽象腔）。
- 其后**至多一段** why，且只写非显而易见的：反直觉行为、负面约束、为什么不用现成方案。
- **禁止**：日期、任务号、`design 决策 N`、进度事件枚举、复述 `package-info`、复述类名。

### 常量 / 字段

- `static final` 的**全大写常量一律保留注释**，哪怕它只是把标识符译成一句人话
  （如 `MAX_COUNT` → 「关键词条数上限。」）。**这不是「复述」**：全大写标识符是把词焊在一起读，
  不经过一次翻译容易被读错或整行跳过——与 `maxCount` 这类可读标识符不是一回事。
- **枚举常量同款保留**：枚举值也是全大写焊词（`SKIP_LOOKUP_DISABLED`），一律留一句人话。
  枚举**类型本身**的注释按上面「类 / 接口」那条判，不适用本条。
- 常量注释同样**只留人话含义与 why，不留决策出处**：可写「30s 是防代理空闲断连的常规值」，
  不写「（design.md「SSE 契约」）」——否则「保留常量注释」会变成决策引用的后门。
- 本条**只覆盖全大写常量与枚举常量**；成员字段与局部变量仍按「删了会不会有人踩坑」判。
- **缺注释、且原因不可从代码推出的，登记而不代写**：例如 `SubtitleStageName` 的六个常量只带
  `("acquire-media", 42)` 这样的裸数字，42 为什么是 42 是**产品口径**，不是能从代码推出来的事实。
  收口时把它登记进待订正清单，**不要自己编一句注释填上**——那是最坏的结果：假注释比没注释糟。

### 公有方法

- 一句话做什么 + 契约（`@param` / `@return` / `@throws`）。
- `@param` 只写：语义、单位、`null` 与缺省的含义、**负面约束**（什么情况别这么传）。
- **禁止**：设计理由、进度事件枚举、实现步骤。
- **可省**：简单 getter、纯委托、显然的 record 访问器——但只是「可省」，
  不确定就不删（「写与删是两件事」）。

### record 参数

- 与 `@Schema(description=…)` 文案重复时**不动**（两边都留着）。
- 只有两份文案**已经不一致或腐坏**时才订正，订正后两份保持一致。
- 类级 `@param` 描述 record **组件**（构造后的字段），构造器级 `@param` 描述**入参**；
  两处各说各的、不重复。

### 私有方法 / 行内注释

- 只写「为什么」，不写「做什么」。自解释的不写。
- **例外必须留**：删了会被当成冗余、实则承载判断的（如 `LlmSubtitleCleanser#baselineOf` 那类守卫）。

### `package-info.java`

- 承接包级架构与边界说明；**这是「上移」的主要目的地**，不是新自由发挥的空间——
  只搬代码里已有的，不顺手扩写。
- **不适用任何行数上限**：它的职责就是承载包级地图（桶结构 + 构件清单 + 依赖方向），天然长于 15 行。

## 四、正例 / 反例（本仓库真实前后对照）

### 反例一：把任务卡的决策记录抄进代码

```java
/** … 空上下文绝不落盘——否则下次会命中这份空缓存，摘要永久丢失且不报错（design 决策 5）。 */
/** … 判定顺序即旧守卫顺序（同语种 → 产物已存在 → 未启用 → 无术语），短路语义与迁移前逐字节一致。 */
/** 翻译子状态（2026-10-02 两段式改造新增）：… */
```

三个问题各占一样：**决策出处**（`design 决策 5`——任务卡归档后没人会去翻，
而且同一份代码里的「决策 5」指的是哪份文档根本无从判断）、**变更史**（`迁移前逐字节一致`）、
**日期**（`2026-10-02`）。三样的共同点是：**它们都在回答「当初怎么变成这样的」，
而读代码的人在问「现在是什么、为什么不能那样改」**。前者归 `git log` 与任务卡，后者才归代码。

### 反例二：类注释变成构件清单

`CheckpointPolicy` 的类注释原本 25 行，其中一段是四个调用方服务名的枚举
（`SubtitlePreparationCoordinator / SubtitleCleanupCoordinator / …`）。
「谁在调我」是**包级地图**，家是 `package-info.java`。

### 正例：`CheckpointPolicy` 收口后（25 行 → 13 行）

```java
/**
 * 检查点语义单源 + 跨批上下文政策（纯函数领域政策，不做文件 I/O）。
 *
 * <p><b>检查点语义</b>：只认「JSON 检查点存在且字节数 &gt; 0」，各调用方合流于此判、不各自判断。
 * <b>SRT 是派生视图，不参与幂等</b>——空转写产出 0 字节 SRT，拿 SRT 当检查点会让空产物永远判
 * 「未完成」，陷入反复重跑的死循环；政策因此不接受任何路径/扩展名入参，SRT 大小进不了判定。
 * 产物在但读不动或解析失败，调用方也照未完成重跑：重跑一遍比留一份坏产物好。
 *
 * <p><b>上下文政策</b>：先读缓存（命中不摘要），没有才摘要（{@link #resolveContext}）；
 * <b>摘要成功才落盘，降级出的空上下文绝不落盘</b>——否则下次会命中这份空缓存，摘要永久丢失且不报错。
 *
 * <p>本类只做裁决，不做 I/O：字节数、文件内容由调用方取好再传进来。
 */
```

**每一句都通过了「删了会不会有人踩坑」**：SRT 那条删了，下一个人会顺手拿 SRT 当检查点，
然后空转写视频陷入死循环；空摘要那条删了，下一个人会把空上下文落盘，摘要永久丢失且不报错。
而「哪四个服务在调它」删了没有代价——`grep` 一下就有。

### 正例：`SubtitleKeywords` 收口后（26 行 → 13 行）

## 五、改代码前去哪找「为什么」

**代码里不再写「为什么这么设计」的长篇，不等于那些知识不存在**——它们按 §二 分流去了四个地方。
要动一段非显然的代码时，按这个顺序找：

1. **`.trellis/tasks/archive/**/design.md`** —— 设计取舍、被否方案、代价的主仓库。
   按主题找，不按日期（`10-11-subtitle-keyword-regenerate` 管关键词与指纹，
   `10-06-domain-logic-sink` 管 domain 政策下沉，`10-06-port-inversion` 管端口定义在域内……）。
2. **`.trellis/spec/**`** —— 规范正文。代码里的 spec 指针（如 `directory-structure.md` 的
   「端口归属判据」）**是保留的**：spec 随仓库走，不是归档品。
3. **`git log -p <file>`** —— 变更史。
4. **`package-info.java`** —— 包级地图。

**这条必须在 review 时主动用**：看到一段代码的 why 缺失，先去这四处找，找不到再问，
不要直接判「注释不够」。

### 边界：本规则管代码，不管 `.trellis/spec/`

「变更史不留」**只作用于源码注释**（`backend/src/**`、`frontend/src/**`）。
`.trellis/spec/` 下**故意**用带日期的修订说明承载规范的演进（如 `error-handling.md` 的
「2026-10-06 改判」「2026-10-12 起覆盖两个场景」）——那是规范文档的既有惯例
（见 `doc-revision-convention`），不是要清的对象。**钩子的扫描面据此不含 `spec/`。**

**这条边界有直接证据**：`TaskConflictException` 类注释里被判为「该删」的那段决策记录，
原文就在 `.trellis/spec/backend/error-handling.md:175`——删代码里的那份，知识 **0 损失**。
收口时遇到同类情形，先到 spec 里确认一遍再删。

**代码里的指针分两类**：

| 指针 | 处置 | 理由 |
|---|---|---|
| `directory-structure.md`「端口归属判据」、`logging-guidelines` 脱敏精神这类 **spec 文档** | **保留** | spec 随仓库走、是一等公民，指向的规则长期有效 |
| `design.md`、`research/**`、`oss-references.md`、任务号、日期这类 **归档品** | **删** | 任务卡归档后没人会去翻，指针是负资产——而且同一份代码里的「决策 5」指向哪份文档根本无从判断 |

## 六、防复发钩子

**形态**：裸装 `.git/hooks/pre-commit`（用户 2026-10-12 选定；由收尾子任务安装）。
命中即非零退出、打印违规行。

### 脚本全文

```sh
#!/bin/sh
# 注释卫生闸：拦住「变更史 / 决策出处」重新长回源码注释。
# 规则出处：.trellis/spec/guides/comment-guidelines.md §六——本脚本就是那一段的全文，别处不再维护第二份。
# 重装：把本段照抄进 .git/hooks/pre-commit 并 chmod +x（Git for Windows 无需 chmod）。
set -e
PATTERN='20[0-9]{2}-[0-9]{2}-[0-9]{2}|[0-9]{2}-[0-9]{2}-[a-z][a-z-]{4,}|设计决策|design 决策|design\.md|research/|oss-references|迁移前|字节一致|旧守卫'
# 只扫已跟踪的源码，避免扫到 target/ 、node_modules/ 、dist/
FILES=$(git ls-files -- 'backend/src/*.java' 'frontend/src/*')
[ -z "$FILES" ] && exit 0
HITS=$(printf '%s\n' "$FILES" | grep -E '\.(java|ts|vue|js)$' | tr '\n' '\0' \
       | xargs -0 -r grep -nE "$PATTERN" 2>/dev/null || true)
if [ -n "$HITS" ]; then
  echo "✗ 注释卫生闸：源码注释里出现了变更史 / 决策出处——"
  echo "$HITS"
  echo
  echo "  日期、任务号、「设计决策 N」、「迁移前 / 旧守卫 / 字节一致」→ 归 git log 与任务卡 design.md"
  echo "  「为什么这样设计」→ .trellis/tasks/archive/**/design.md，代码里至多留一句 why"
  echo "  spec 指针（*.md 规范文档）不受本条约束。"
  echo "  确认无误要提交：git commit --no-verify"
  exit 1
fi
exit 0
```

### 模式清单（**只此一处**；任务卡的 AC1 与各层执行脚本都照抄这里，不维护第二份）

| 模式 | 拦的是 |
|---|---|
| `20[0-9]{2}-[0-9]{2}-[0-9]{2}` | 日期 |
| `[0-9]{2}-[0-9]{2}-[a-z][a-z-]{4,}` | 任务卡 slug（如 `10-11-subtitle-keyword-regenerate`） |
| `设计决策` / `design 决策` | 决策出处（**中文与英文两种写法都要拦**——2026-10-12 实测只用 `design 决策` 漏掉了 5 处） |
| `design\.md` / `research/` / `oss-references` | 任务卡与归档研究索引的指针（`oss-references.md` 自己写着「**索引不是规格**…只读摘要等于二手转述」，指向它尤其没意义） |
| `迁移前` / `字节一致` / `旧守卫` | 变更史叙事 |

### 已知缺口（不假装它没有）

- **不入库**。`.git/hooks/` 不被 git 跟踪，换机器或重新 clone 后钩子消失、且**静默失效**。
  缓解：上面有脚本全文，可据此手工重装。这是权衡后接受的代价。
- 可用 `git commit --no-verify` 绕过——它是**防手滑**，不是防绕过。
- **模式清单是高频形态，不是穷举**。`原为…`「原先…」「已被 X 取代」这类改写叙事拦不住，
  靠 review 与 §二 的分流表。**实测漏检过的自然语言变体**：`与原 normalize 公式一致`（而模式只列了 `原为`）。
- **已知误报（不为此收窄模式，靠 review 排除）**：`StageProgress` / `ProgressListener` 里的
  「分层**倒置**」是概念词，不是变更史。
- **短任务号（`09-28 的实证…`）也拦不住**：它既不是 `20xx-xx-xx` 日期，也不带 slug 尾缀，
  两个模式都不匹配（域内试点时漏检一处）。补 `(0[1-9]|1[0-2])-[0-3][0-9]` 会误伤版本号与文件名，
  权衡后**不加**，靠人眼。
- `research/` 这条可能误伤——真需要指向 `research/` 目录的注释请用 `--no-verify` 并说明理由。
- Git for Windows 经自带的 sh 执行 hook，脚本必须带 `#!/bin/sh` 且**无 CRLF**。
  实测不生效时的退路：把同一段放 `tools/check-comment-hygiene.sh` 并手工调用。

## 七、元规则：标准只住一处

**规则正文只能住 `.trellis/spec/`**——spec 随仓库走、每个任务自动读到；任务卡归档后没人会翻。
其他地方**只能引用，不能复制**。

### 三种已知的复制陷阱（2026-10-12 本任务全踩过）

| 陷阱 | 长什么样 | 怎么防 |
|---|---|---|
| **草稿晋升后没退休** | 规划期把标准草稿放在任务卡 `design.md`；正典落地后草稿没降格，继续当权威。本任务的父 `design.md` 就这样漂到「七条禁令版」，而正典已十三条 | 正典一落地，**同一次改动里**把草稿改成指针 |
| **诊断表长得像规则表** | prd「问题定义」里的那张「内容 → 真正的家」表，形状就是分流规则，且证据来自更早的版本，天然落后 | 诊断表下加一句「规则以正典为准，本表只说明当初为什么这么判」 |
| **可执行命令里的模式串** | 执行脚本会想照抄一份 grep 模式，于是四处同源、改一处漏三处 | 模式清单**只住正典 §六**；脚本写「照抄正典 §六」，不维护第二份 |

### 副本只允许两种身份

1. **指针**——一句「正文见 X」；
2. **极短摘要**——如两份 `quality-guidelines` 的三句话入口 + 各自语言的例子，**且必须写明「规则正文见正典」**。

**判据**：同一段规则文字出现在两个文件里 → 其中一个必然是副本。就地问它是（a）还是（b），
都不是就删掉。
